# Project Memory

## Durable decisions

- The original Gradio application is retained as a runnable historical implementation.
- The version 0.3.0 product-facing implementation lives in `expert_platform/` and separates a FastAPI backend from a Vue 3 TypeScript frontend. The browser talks only to the documented HTTP API; the backend reuses `apps.pdf_learning_assistant.PDFLearningAssistant`, which composes `hello_agents_framework`, so the separated application does not fork the Agent, memory, RAG, or provider code paths. The Gradio entry point remains a historical comparison path rather than the default product entry.
- The separated backend stores hashed web-session tokens only in the existing SQLite `expert_web_sessions` table and keeps one `PDFLearningAssistant` runtime per authenticated browser session in process. Separate valid browser/device logins to the same account remain supported and do not share current-session conversations or counters; closing a browser is not logout, and no valid session is evicted by age or count before its recorded expiry. Backend initialization and login remove expired/orphaned rows, resolving an expired or orphaned presented token removes that exact row, re-login replaces only the current browser cookie's row, and logout is idempotent. The durable cookie can survive a backend restart, but current-session state is intentionally process-local. `expert_platform/backend/app/demo.py` is an isolated in-memory browser-QA fixture whose SQLite state lives under `/tmp`; it is not a product entry point and must never use the project database.
- Existing framework components remain the source of truth for user accounts, knowledge metadata, RAG indexing, retrieval, and model access.
- `共享专家库` is the sole system-owned shared expert, identified by owner `__shared__`, knowledge-base ID `default`, and namespace `pdf_shared_default`. Every authenticated user may read from and upload to it. A private expert belongs to exactly one user. `所有专家` is a read-only aggregate view of the shared expert plus the signed-in user's private experts.
- Authentication uses an opaque server-side session stored in SQLite and an HttpOnly cookie; passwords remain managed by the existing `UserAccountStore`.
- RAG resources are initialized lazily so login, expert management, and metadata browsing remain available when Qdrant or an embedding provider is unavailable.
- Advanced MQE/HyDE retrieval is an optional quality enhancement, not an availability boundary: provider failures fall back once to ordinary vector retrieval. When evidence retrieval succeeds but final answer generation fails, both Gradio and the separated web application return attributed source excerpts rather than losing the question behind a generic 503. Logs retain redacted exception types only.
- The workspace root is the shared configuration boundary for the numbered projects: the root `.env` contains model and service settings, while `workspace_llm.py` is a compatibility client used only by projects that explicitly import it. Project 12 does not depend on `workspace_llm.py`; its reusable `hello_agents_framework` reads the same environment through its own `core/config.py`, `core/llm.py`, and embedding adapters. The historical Gradio app and the `expert_platform` web application should load the root `.env` but obtain Agent, tool, memory, RAG, and LLM behavior from `hello_agents_framework`. UI, authentication/session handling, authorization, product workflow, and domain policy remain application-layer responsibilities.
- Temporary remote development access uses `app.linkwise.site` through Caddy and a reverse SSH tunnel to the local Vite server. Keep that exact hostname in Vite's `server.allowedHosts`; do not replace it with an allow-all setting. This is a development/demo path. A production-style path should build the frontend and tunnel or proxy the FastAPI server that serves `frontend/dist/`, rather than expose the Vite development server.
- Personal reporting uses a rolling 30-day window over complete, user-scoped `qa_interaction` records in `episodic_memories`, grouped by the expert identity captured when each conversation completed. Each new event stores the structured question and final user-visible answer, so reports span browser sessions and backend restarts; legacy events without an answer are excluded rather than summarized incompletely. The model receives at most the newest 30 turns per expert. Generated snapshots are atomically stored as one file per user and generation month under `monthly_personal_reports/<user_scope>/`; legacy `learning_reports/` files remain untouched.
- The note feature is retired from both Vue/FastAPI and Gradio. `PDFLearningAssistant` no longer creates or lists `learning_note` events, `/api/notes` no longer exists, and the frontend has no note controls or note browsing. On 2026-08-14 the sole existing `learning_note` row and its same-ID point in `hello_agents_practice_episodic_1024` were deleted; the shared `episodic_memories` table, its user/time index, and Q&A/document events remain because monthly reports depend on them.
- On 2026-08-15, legacy per-user `default`/`共享知识库` catalogs and all data belonging to `eric`, `Jenny爱菲`, `codexqa0807`, `web_user`, and `default_user` were removed from `practice_memory.db`, active knowledge-base storage, and the two practice Qdrant collections. The retained canonical shared expert is `__shared__/default/pdf_shared_default`; `ljm` private experts and data remain. A recoverable pre-cleanup backup is stored under `.runtime/data-cleanup-backups/20260815-110416/`.
- On the document-management page, the selected browse scope is also the upload target. The global chat expert selection must not determine document uploads, and the aggregate `所有专家` scope is read-only with upload disabled.
- Expert-document management uses backend `limit`/`offset` responses with `{ items, total }` and a fixed Vue page size of 10. Scope and submitted-search changes reset to page one; deleting the only record on a later page moves back one page. The current assistant adapter filters and orders accessible summaries before slicing, so storage-level pagination should be introduced only if measured catalog size makes that metadata scan material.
- Destructive local maintenance uses `python -m expert_platform.cli.delete_data`, backed by the shared deterministic domain module `expert_platform/backend/app/admin_deletion.py`: SQLite resolves ownership and namespace, dry-run is the default, the shared expert is protected, and explicit execution synchronizes active SQLite, `knowledge_base`, monthly-report, and practice-Qdrant data according to user/expert/document scope. List arguments support multiple users, multiple experts under one user, and multiple documents under one user/expert pair; all targets are preflighted before one confirmation and then run sequentially. Stop FastAPI before execution. Expert deletion intentionally preserves historical Q&A; only user deletion removes episodic history and sessions.
- The expert-platform Vue UI ships a dependency-free `zh-CN`/`en-US` locale catalog. The browser-local `expert-platform:locale` setting is independent of authentication and applies to login, application navigation, Q&A, expert management, monthly reports, profile, document metadata formatting, and accessibility labels. User-authored content, custom names, model output, report content, and backend messages are preserved in their source language.
- The Expert Platform admin console remains inside the same Vue/FastAPI website at `/admin`; ports and hidden navigation are not authorization boundaries. SQLite `expert_admin_roles` grants privilege by immutable user ID, every admin API request rechecks that role, and local `python -m expert_platform.cli.manage_admin` owns create/grant/revoke/list operations. Administrative deletion shares `expert_platform/backend/app/admin_deletion.py` with the local CLI, requires same-origin preview plus exact-ID confirmation, protects administrator accounts and the shared expert, and writes metadata-only audit events after success.
- Admin disk usage means retained original document-file bytes only. Document rows stat their validated `source_path`; expert rows sum managed documents in that namespace; user rows sum managed documents across owned experts. All three lists sort this value descending before pagination. Missing files, malformed metadata, symlinks resolving outside `knowledge_base/`, and arbitrary external paths count as zero. Do not attribute shared SQLite pages, Qdrant segments/indexes, caches, or reports to individual documents without a separate evidence-backed accounting model.
