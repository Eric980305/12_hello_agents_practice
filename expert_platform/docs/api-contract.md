# API Contract

All routes use the `/api` prefix. JSON fields use camelCase. Errors use
`{ "detail": "user-readable message" }`.

Authentication uses the `expert_session` HttpOnly cookie. The frontend sends
credentials with every API request.

## Authentication

- `POST /api/auth/register` `{ username, password }` -> `201 { user }`
- `POST /api/auth/login` `{ username, password }` -> `{ user }` and session cookie;
  if the request already presents a session cookie, that current browser session is
  atomically replaced while other browser/device sessions remain valid
- `POST /api/auth/logout` -> `204` and removes the current session cookie; logout is
  idempotent even when the server-side session is already missing or expired
- `GET /api/auth/me` -> `{ user }`
- `GET /api/bootstrap` -> `{ user, experts, sessionId }`

`user` is `{ id, username, vipLevel, balance, isAdmin }`. `isAdmin` is derived only
from the server-side `expert_admin_roles` table; a username has no implicit role.
Repeated failed login attempts for one client/username pair return `429` with a
`Retry-After` header during the bounded lockout window.

The session store removes expired and orphaned rows at backend initialization and
before issuing a new token. Resolving an expired or orphaned presented token deletes
that exact row. Closing a browser is not logout: the persistent cookie remains valid
until explicit logout or expiry, and valid sessions are never removed by age or a
per-user count limit before `expires_at`.

## Experts

- `GET /api/experts` -> `{ items }`
- `POST /api/experts` `{ name }` -> `201 { item }`
- `DELETE /api/experts/{expertId}` `{ confirmed: true }` ->
  `{ deletedExpertId, deletedDocuments }`

Each expert is `{ id, name, kind, deletable }`. The list starts with the read-only
aggregate `{ id: "__all__", name: "所有专家", kind: "aggregate" }`.

## Documents

- `GET /api/documents?expert_id=&query=&limit=&offset=` -> `{ items, total }`
- `POST /api/documents` multipart fields `expert_id` and `file` ->
  `201 { result, items, total }`
- `DELETE /api/documents/{documentId}?expert_id=&confirmed=true` -> `204`

Document items are `{ id, fileName, sourceType, expertId, expertName, createdAt }`.
The expert document UI requests `limit=10`; filtering and newest-first ordering occur
before the backend applies `offset` and `limit`. `total` is the complete number of
matching documents in the selected expert or aggregate scope.
Upload requires one concrete expert. The backend rejects an empty file, unsupported
format, or payload over 50 MB before reporting success.

## Chat

- `GET /api/chat/history` -> `{ items }`
- `POST /api/chat` `{ expertId, question, advanced }` -> `{ message }`

Chat requires one concrete expert. A message is
`{ id, role, content, expertId, expertName, createdAt }`. Source labels remain in the
grounded answer text generated by the existing product service.

## Monthly personal reports

- `POST /api/reports/monthly` -> `{ report }`

The report contains:

- `period`: rolling UTC range `{ startTime, endTime, days }`.
- `generatedAt` and `reportMonth`.
- `metrics`: `{ conversationCount, conversationsUsed, expertsUsed }`.
- `summary`: the combined Chinese summary grouped by expert.
- `expertSummaries`: each expert's ID, name, conversation count, and summary.

The backend derives the user from the authenticated cookie and reads only that user's
complete `qa_interaction` events from the previous 30 days. It uses at most the newest
30 turns per expert, writes one atomic JSON snapshot for the current generation month,
and never accepts a user ID from the browser. Legacy events without a stored answer
are excluded because they cannot support a faithful conversation summary.

## Health

- `GET /api/health` -> `{ status: "ok", version: "0.3.0" }`

## Administration

Every route below requires a valid authenticated session whose user ID has an active
administrator role. Unauthorized and authenticated non-admin callers receive `401`
and `403` respectively. Destructive preview and execute requests also require a
same-origin `Origin` header.

- `GET /api/admin/overview` -> `{ counts, vectorStore }`
- `GET /api/admin/users?query=&limit=&offset=` -> `{ items, total }`
- `GET /api/admin/experts?query=&user_id=&limit=&offset=` -> `{ items, total }`
- `GET /api/admin/documents?query=&user_id=&expert_id=&limit=&offset=` ->
  `{ items, total }`
- `POST /api/admin/deletions/preview`
  `{ action, userId, expertId?, documentId? }` -> `{ plan, confirmationText }`
- `POST /api/admin/deletions/execute`
  `{ action, userId, expertId?, documentId?, confirmation }` -> `{ deleted }`

`action` is `user`, `expert`, or `document`. Preview and execute resolve the account,
expert, namespace, document, SQLite rows, Qdrant points, and filesystem targets from
authoritative storage. Execute rebuilds the plan, requires `confirmation` to equal the
exact target ID, rejects every administrator account and the shared expert, invalidates
affected in-process assistants after success, and appends a metadata-only audit event.

Admin list responses never include password hashes, salts, session tokens, document
contents, chunk contents, vector contents, provider responses, or secrets. Qdrant
unavailability is reported as degraded status for the overview and blocks destructive
preview/execution rather than presenting incomplete impact as safe.

User, expert, and document items include `diskBytes` as a non-negative integer. It
measures retained source files only, not shared SQLite database pages, Qdrant storage,
indexes, caches, or reports. All three list endpoints order by `diskBytes DESC` before
applying `limit` and `offset`; stable identity fields break ties.
